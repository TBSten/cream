# Refactor by cream.kt skill

Finds handwritten property-copying boilerplate in an existing Kotlin project and replaces it with
copy functions generated by [cream.kt](https://github.com/TBSten/cream).

The goal of every refactoring in this skill is the same: **leave only the values that actually
change at the call site**, and let cream generate the carry-over. Reviewers then see the diff, not
the boilerplate around it.

## Prerequisites

- [ ] KSP and cream.kt are set up in the target module.
    - If they are not, set them up first with the
      [setup-cream skill](https://github.com/TBSten/cream/blob/main/doc/ai-integration/skills/setup-cream/SKILL.md).
      Use a subagent for it if subagents are available.
- [ ] The working tree is clean, or the user has confirmed that uncommitted changes are fine.
      This skill rewrites existing code; the user needs a way back.

## Refactoring targets

- [ ] State management in a ViewModel — or an equivalent StateHolder or Presenter. -> [./viewmodel.md](./viewmodel.md)
- [ ] Mapping between domain models and data models. -> [./model-mapping.md](./model-mapping.md)

## Workflow

### 1. Confirm the targets and the verification method with the user

Search the project for files that could be refactored. Each target file above lists the concrete
signals to grep for.

If nothing refactorable turns up, say so and stop. Do not invent work — a project with no
hand-written carry-over has nothing for this skill to do.

If candidates are found, ask the user which of the targets to actually refactor. Use an Ask-style
tool if one is available.

Then inspect the project's build setup, work out which verification methods are available, and ask
the user which one to use.

Example asks:

```
Q1. Which files should be included in the refactoring?

- [ ] ~ViewModel
  - Rewrites the state-transition code inside the ViewModel to use cream's generated copy functions.
- [ ] :data:remote module
  - Rewrites the data model <-> domain model mapping functions to use cream's generated copy functions.
```

```
Q2. How should the result be verified?

- [ ] Confirm the test task passes
- [ ] Compile only
- [ ] Do not verify
```

Notes:

- Match the call convention and the way choices are presented to whichever Ask tool is available.
- Ending your turn to wait for user input without calling an Ask-style tool is a last resort.

### 2. Implement and verify, one target at a time

Work through the targets the user selected. The concrete procedure for each lives in the file
linked from [Refactoring targets](#refactoring-targets).

If subagents are available, launch one per target and work in parallel.

Whatever the target, hold to these rules:

- **Refactor in small steps and verify after each one.** One state machine, or one mapping
  function, at a time. A large batch of edits that fails to compile is hard to unwind.
- **Behaviour must not change.** A generated default is only correct when it copies the same value
  the hand-written code did. Where the old code deliberately passed something *other* than the
  previous value — a reset to a default, a cleared error, a dropped snackbar — that argument must
  stay explicit at the call site. Read what the old code did; do not assume.
- **Delete the code you replaced.** Leaving the hand-written mapper next to the generated one is
  worse than not refactoring at all.
- **Stay on cream's defaults.** Every KSP option and every `funName` you write is configuration the
  project then has to maintain, and this refactoring is not the place to introduce it. Add one only
  when the user asked for it, or when the default is demonstrably wrong for this code and you have
  said why — never to make the result match an example in these instructions.
- **Verify with the method the user chose** in step 1, and report honestly if it fails. That
  answer governs for every target — the per-target files defer to it and never upgrade it on their
  own. If it looks too weak for what a target actually changed, say so in the report rather than
  running more than you were asked to.

### 3. Report

Tell the user, per target: which files changed, how many hand-written copies were removed, which
cream annotations were added, and the result of the verification step. Call out anything you
deliberately left alone and why.

## Troubleshooting

**Unresolved reference to the generated function, in a Kotlin Multiplatform module**

The `commonMain` workaround is missing or was not applied to this module. KSP does not generate
into intermediate source sets, so without it the generated code is invisible to `commonMain`. See
[Kotlin Multiplatform support](https://github.com/TBSten/cream/blob/main/doc/customization/multiplatform.md).
Note also that with the workaround applied, annotations in platform source sets
(`androidMain`, `jvmMain`, `iosMain`) are **not** processed — annotated classes must be in `commonMain`.

**The generated function has a different name than expected**

Function names come from `cream.copyFunNamePrefix` and `cream.copyFunNamingStrategy`, so
`copyTo<TargetName>` is only what the defaults produce. Read the generated file under
`build/generated/ksp/` to see the real name rather than guessing. To change it module-wide, set
those options; to pin one declaration's name, use the annotation's `funName` argument. See
[Function name](https://github.com/TBSten/cream/blob/main/doc/customization/fun-name.md).

**"No value passed for parameter" on a generated function**

This is by design, not a bug. cream only generates a default for a property whose **name and type**
both match. A mismatched type gets no default, so the compiler forces you to supply the conversion.
Pass it explicitly; that line is the one worth reviewing.

With the default options a `value class` wrapper counts as a mismatch too, so `String` -> `ItemId`
stays required. Automatic value class mapping, which generates the wrap for you, is opt-in from
0.10.0 (`cream.autoValueClassMapping=true`) — see the note in
[./model-mapping.md](./model-mapping.md#the-generated-name-and-whether-you-still-need-a-wrapper).

**A property is silently wrapped or unwrapped through a `value class`**

This only happens when the module opted in with `cream.autoValueClassMapping=true` (available from
0.10.0); remove that option to get the parameter back as required. See
[Value class mapping](https://github.com/TBSten/cream/blob/main/doc/customization/value-class-mapping.md).

**`@CopyToChildren` generated a copy function to an `object` you did not want**

Set `cream.notCopyToObject=true` module-wide, or `notCopyToObject` on the annotation. See
[@CopyToChildren](https://github.com/TBSten/cream/blob/main/doc/copy-to-children.md).

**A property should never get an auto-copied default**

Use `.Exclude` so the parameter keeps its place in the signature but loses the `= this.<property>`
default. **Where it goes differs per annotation** — `@CopyTo.Exclude` on the source class's
constructor parameter, `@CopyFrom.Exclude` / `@CombineFrom.Exclude` on the target's,
`@SealedCopy.Exclude` / `@CopyToChildren.Exclude` on the sealed parent's property. For
`@CopyMapping` / `@CombineMapping`, which cannot annotate the classes, use the `excludes` argument
with target-side property names. See the placement table in
[Exclude](https://github.com/TBSten/cream/blob/main/doc/customization/exclude.md).

**Editing the annotation changes nothing / the generated code looks stale**

Re-run the KSP task (`:<module>:kspCommonMainKotlinMetadata` on KMP), and `./gradlew clean` if it
still does not update. Check the generated file on disk before concluding that cream is at fault.

**Another KSP processor in the module stopped running**

The KMP workaround disables every non-metadata `ksp*` task, including other processors'. Narrow
the `if` condition so their tasks stay enabled.
